# Security and Privacy Checklist: Operator Sign-in

**Purpose**: Test whether the requirements of spec 010 say enough, clearly and consistently, about who may get into the operators console, what an attacker can learn or cause, what ends a session, and what is kept about a sign-in — before implementation.

## The First Operator

- [ ] CHK001 Is it specified who is allowed to run the deployment operation and what is recorded about each run — who ran it, when, for which account — as a requirement of the spec and not only as a plan decision? [Completeness, Spec §FR-003, research R9]
- [ ] CHK002 Is it specified what happens when the operation is run with a mistyped email — whether an invited account can be withdrawn or corrected before its link is used, given that the link alone makes its holder an operator? [Gap, Spec §FR-003, §FR-004]
- [ ] CHK003 Is the number of operators the operation may create bounded or explicitly unbounded, so that "the first operator" and "any operator, before spec 011" are not two readings of the same requirement? [Ambiguity, Spec §FR-003, User Story 5a]
- [ ] CHK004 Is it stated that possession of the first-password link is the only proof asked of an invited operator, and is that accepted in writing for an account with the widest reach in the product? [Assumption, Spec §FR-004a]

## What an Attacker Can Learn

- [ ] CHK005 Is "indistinguishable in time" given a measurable threshold — a statistic and a margin — rather than "cannot be told apart over a hundred tries"? [Measurability, Spec §FR-011, §SC-003]
- [ ] CHK006 Is the single-answer rule stated for every address that takes an email or a token before sign-in — forgot password, reading a link, setting a password, resending a code — and not for the sign-in form alone? [Coverage, Spec §FR-010, §FR-025, §FR-027]
- [ ] CHK007 Do the two answers for a link that no longer works — "send a new one" for a reset, "ask whoever sent it" for a first password — reveal to a stranger that an account exists and is still invited, and is that disclosure accepted and stated? [Clarity, Spec §FR-004a, §FR-027]
- [ ] CHK008 Is it specified that the lock warning and «هذا الحساب موقوف.» are the only things said after a correct password, and that nothing else about the account (last sign-in, name, role) is returned before the code is accepted? [Completeness, Spec §FR-012]
- [ ] CHK009 Is it specified what the "reason" shown on the sign-in screen after a session ended may reveal to someone who holds only an ended session's cookie, and that a reused session value is deliberately explained as an ordinary ended session? [Consistency, Spec §FR-035, contracts/operator-sessions.md §3]

## What an Attacker Can Cause

- [ ] CHK010 Is it stated and accepted that anyone who knows an operator's email can lock that account for fifteen minutes at a time by sending five wrong passwords, including the only operator's, and is there a requirement that limits how long this can be kept up? [Gap, Spec §FR-015, §FR-016]
- [ ] CHK011 Are the request limits specified for each address before sign-in — sign-in, code, resend, forgot, reading a link, setting a password — or only for "sign-in requests"? [Clarity, Spec §FR-009, User Story 10]
- [ ] CHK012 Is the effect of the per-address limit on several operators working behind one office address specified — ten requests a minute shared among all of them — and accepted or adjusted? [Edge Case, Spec User Story 10, Gap]
- [ ] CHK013 Is it specified whether asking for reset links can be used to flood an operator's mailbox, beyond "one a minute for an account", and whether asking for a link ends a sign-in in progress? [Clarity, Spec §FR-026, Edge Cases]
- [ ] CHK014 Is protection against a request forged from another site a requirement of the spec for every address that changes something, rather than a line of the API contract's description? [Gap, contracts/operators-api.openapi.yaml]
- [ ] CHK015 Is it stated that one operator signing in ends another device's session by design, so that a thief who signs in also signs the operator out — and what the operator is told to do when they see "signed in on another device" without having done it? [Completeness, Spec §FR-030, §FR-033a]

## The Second Factor and the Mailbox

- [ ] CHK016 Is it stated and accepted that the reset link, the sign-in code and the new-browser notice all go to the same mailbox, so that whoever controls the mailbox controls the account with no other factor? [Assumption, Spec §FR-007, §FR-026, §FR-033a]
- [ ] CHK017 Is it specified whether changing the password while signed in asks for anything beyond the current password — the email code again, for instance — and is the choice justified for an unattended, unlocked console? [Gap, Spec §FR-045]
- [ ] CHK018 Are the contents of the code's email and the new-browser notice specified precisely enough to be checked — what each must say, must not contain, and in which language — or left as wording for the owner without a requirement behind it? [Measurability, Spec §FR-024, §FR-033a, §FR-055]
- [ ] CHK019 Is "a browser the account has not signed in from before" defined so that its limits are stated — cleared cookies, a private window, a second profile — and is the resulting number of notices accepted? [Clarity, Spec §FR-033a, Key Entities]
- [ ] CHK020 Is a password's strength specified beyond length and character classes — a refusal of well-known or already-leaked passwords, or of the account's own name and email — or is the absence of such a rule a stated decision? [Gap, Spec §FR-029, §FR-046]

## Sessions

- [ ] CHK021 Is "activity" defined in the spec in a way the platform itself can decide, given that the console marks its own background requests and a holder of the session could leave the mark off? [Clarity, Spec §FR-032, contracts/operator-sessions.md §4]
- [ ] CHK022 Is the risk of «تذكرني» on a shared or borrowed machine addressed in the requirements — a warning beside the box, or its absence stated as accepted? [Gap, Spec §FR-033]
- [ ] CHK023 Are the events that end a session listed once and consistently between the spec's requirement, its acceptance scenarios and the sessions contract — including the fifth wrong current password and a reused session value? [Consistency, Spec §FR-031, §FR-035, contracts/operator-sessions.md §3]
- [ ] CHK024 Is "refused at once" quantified for every way a session ends — the very next request, and within thirty seconds on an untouched console — and is the thirty seconds stated for a reset and a suspension as well as a sign-in elsewhere? [Measurability, Spec §FR-030, §FR-031, §SC-005, §SC-006]
- [ ] CHK025 Is it specified what a sign-in in progress (after the password, before the code) may do and for how long, and that it is ended by a completed reset, a suspension and a lock? [Completeness, Spec §FR-023, §FR-028, Edge Cases]
- [ ] CHK026 Is the separation of the two consoles specified for an operator who is also a clinic team member with the same email and the same browser — two sessions side by side, each unaffected by the other's sign-out, lock and reset? [Coverage, Spec §FR-002, §FR-037, Edge Cases]

## What Is Kept, and for How Long

- [ ] CHK027 Is a retention period stated for the records of sign-in events, or an interim one until specs 023 and 025 decide, given that they hold addresses and device names of named people? [Gap, Spec §FR-052, Assumptions]
- [ ] CHK028 Is how long ended sessions, known browsers and used links are kept a requirement of the spec, rather than figures that appear only in the plan (ninety days, four hundred days, one day)? [Consistency, Spec §FR-038, §FR-043, research R13]
- [ ] CHK029 Is it specified who can read the sign-in records before the operators' audit log and security events exist, and whether anyone is alerted to a lock or a reused session value in the meantime? [Gap, Spec §FR-052, Out of scope]
- [ ] CHK030 Are "log", "record" and "operational log" used with one meaning each, so that "an email address must not appear in operational logs" and "each event is recorded with who" cannot be read as contradicting each other? [Clarity, Spec §FR-052, §FR-053]
- [ ] CHK031 Is it specified what is recorded for a sign-in attempt on an email that belongs to no operator — enough to see an attack, without keeping the address typed? [Completeness, Spec §FR-052, §FR-053, research R6]

## Access Inside the Console

- [ ] CHK032 Is "every signed-in operator reaches the frame, the home and their own profile, and nothing else" stated so that a later spec cannot add an address every operator may reach without naming who may use it? [Clarity, Spec §FR-039, §FR-040]
- [ ] CHK033 Is it specified that the profile shows and changes only the signed-in operator's own account, with no identifier of an account anywhere in its addresses? [Completeness, Spec §FR-041, §FR-043]
- [ ] CHK034 Are the paths that cannot be reached through the product until spec 011 — a suspended operator, a changed role, a lock lifted by another operator — each stated as built and tested here, or as left for that spec, without overlap? [Consistency, Spec §FR-016, §FR-035, plan Constitution Check VII]
