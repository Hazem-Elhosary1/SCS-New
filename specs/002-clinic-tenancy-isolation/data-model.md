# Data Model: Clinic Tenancy and Data Isolation

Schema `tenancy`, owned by the new `Tenancy` module and migrated before every other module that
has clinic-owned tables.

## Clinic-owned

### `tenancy.Clinic`

The owner of data. The one table where the clinic's id is the row's own key.

| Field | Type | Rules |
|---|---|---|
| `Id` | uniqueidentifier, PK | Version-7 GUID generated by the application; never changes |
| `ClinicId` | uniqueidentifier, NOT NULL | Always equal to `Id` (check constraint); the column isolation is applied on |
| `NameAr` | nvarchar(200), NOT NULL | Display name in Arabic; 1 to 200 characters after trimming |
| `NameEn` | nvarchar(200), NOT NULL | Display name in English; 1 to 200 characters after trimming |
| `State` | nvarchar(20), NOT NULL, default `active` | The states and their meaning are spec 016. Here only one rule reads it: `suspended` and `cancelled` are "not publicly available" on the patient address (FR-033) |
| `CreatedAtUtc` | datetimeoffset, NOT NULL | Set once |

Isolation: security policy `tenancy.ClinicIsolation` with the five predicates on `ClinicId`.
A clinic reads its own row; another clinic's row is invisible.

The current short name is **not** stored here: it is the directory entry marked current, so
there is one source of truth and a rename is one change.

The application login is denied insert, update and delete on the whole `tenancy` schema, by the
administrator's login script. A clinic's own work can therefore read its record but never change
it — in particular it cannot change its own `State`. Only the operator connection writes here.

## Platform-wide (declared in `PlatformWideTables`)

### `tenancy.ClinicDirectory`

Every short name a clinic has ever had. This is what resolves a patient address before any
clinic is established, so it is readable by the application login without a clinic.

| Field | Type | Rules |
|---|---|---|
| `ShortName` | nvarchar(40), PK | Canonical form. Being the key is what stops a name being reused by another clinic |
| `ClinicId` | uniqueidentifier, NOT NULL, FK → `Clinic.Id` | The clinic the name leads to |
| `IsCurrent` | bit, NOT NULL | Exactly one current name per clinic (filtered unique index on `ClinicId` where `IsCurrent = 1`) |
| `AssignedAtUtc` | datetimeoffset, NOT NULL | When the name was given |

Holds nothing but names that already appear in public addresses.
The application login can read it; only the operator connection writes it.

### `crossing.CrossClinicAccess`

One row per use of an operator crossing (FR-027).

| Field | Type | Rules |
|---|---|---|
| `Id` | bigint identity, PK | |
| `Operation` | nvarchar(60), NOT NULL | One of the names in `DeclaredCrossings` |
| `ClinicId` | uniqueidentifier, NULL | The clinic acted on; null for an operation over all clinics (list) |
| `OperatorId` | nvarchar(100), NOT NULL | The operator; until spec 010, the name of the tool or test |
| `TraceId` | char(32), NULL | Request reference, when there is one |
| `OccurredAtUtc` | datetimeoffset, NOT NULL | |

Identifiers only. Append-only: the application never updates a row, and deletes one only when
it is older than the retention period (FR-032). The period is the configuration value
`SCS_RETENTION__CROSS_CLINIC_ACCESS_DAYS`, default `1825` (5 years), not secret, minimum `30`.
A daily job, `tenancy-purge-access-records`, removes older rows through the declared crossing
`purge-access-records` and logs how many it removed.

It lives in its own schema, `crossing`, so that the administrator's login script can deny the
application login every right on that schema. A clinic's work therefore cannot read who looked
at which clinic, and the denial does not depend on the application or the migrator.

### Already platform-wide from spec 001

`platform.JobHeartbeat`, each module's `__EFMigrationsHistory`, and everything in schema
`hangfire`.

## Database objects that are not tables

| Object | Purpose |
|---|---|
| `tenancy.fn_ClinicAccess(@ClinicId uniqueidentifier)` | Inline, schema-bound function every policy calls. Returns a row when `@ClinicId` equals the session's `ClinicId`, or when the user is in `scs_cross_clinic` |
| Role `scs_cross_clinic` | Members `scs_ops` and `scs_migrator`. Created by an administrator, not by the application |
| Login `scs_ops` | The operator connection. Read and write; no structure rights |
| Login `scs_report` | Hand-written report queries (`IClinicConnection`). Read only, under the same isolation as the application login; configuration value `SCS_DB__REPORT_CONNECTION` |
| Schemas `tenancy` and `crossing` | Created by the administrator's login script, which is also where the application and report logins are denied writes on `tenancy` and everything on `crossing` |
| Security policy per clinic-owned table | `<schema>.<Table>Isolation`; created by `CreateClinicIsolation` in the migration that creates the table |

## Not stored

### Clinic context

Which clinic a piece of work is for. Exists for the duration of one request or one job.

| Attribute | Rule |
|---|---|
| `ClinicId` | Null until established |
| `Source` | `patient-address`, `account` (from spec 003) or `job` |
| Establish | Once. A second call with the same clinic is a no-op; with a different clinic it is refused (`CLINIC_MISMATCH`) |

### Short name (value)

| Rule | Value |
|---|---|
| Canonical form | Lower case; surrounding spaces and slashes removed |
| Pattern | `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` |
| Length | 3 to 40 |
| Field codes on refusal | `REQUIRED`, `TOO_SHORT`, `TOO_LONG`, `INVALID_FORMAT`, `RESERVED`, `TAKEN` |

### Reserved words

One list in the Tenancy module. Starting content:

`api`, `app`, `assets`, `i18n`, `fonts`, `media`, `health`, `v1`, `config`, `version`,
`favicon`, `index`, `static`, `public`, `admin`, `ops`, `operator`, `operators`, `support`,
`help`, `login`, `logout`, `signin`, `signup`, `account`, `www`, `mail`, `status`, `docs`,
`clinic`, `clinics`, `patient`, `patients`, `heta`, `scs`.

Later specs add to it and never remove from it.

### Declared crossings

| Name | What it does | Used by |
|---|---|---|
| `register-clinic` | Creates a clinic and its first short name | Seed tooling now; spec 015 |
| `rename-clinic` | Gives a clinic a new current short name; keeps the old one | Spec 015 |
| `list-clinics` | Lists clinics | Spec 015 |
| `list-clinic-ids-for-jobs` | Lists clinic ids so a per-clinic job can fan out | Job scheduler |
| `purge-access-records` | Removes access records older than the retention period | Daily job |

## Relationships

```text
Clinic 1 ── * ClinicDirectory (exactly one IsCurrent)
Clinic 1 ── * CrossClinicAccess (optional)
Clinic 1 ── * every clinic-owned row in every module, through ClinicId
```

## Rules every clinic-owned table follows (for later specs)

1. Column `ClinicId uniqueidentifier NOT NULL`, with a foreign key to `tenancy.Clinic(Id)`.
2. `ClinicId` is the leading column of the primary key or of every index used for lookups.
3. Unique constraints include `ClinicId`, unless the spec says a value is unique across clinics.
4. The security policy is created in the same migration as the table.
5. The entity implements `IClinicOwned`, and the test project has an `IIsolationSample<T>` for it.
